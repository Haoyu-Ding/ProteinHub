ProteinHub production rollout

服务器部署步骤和每一步的意义

这份页面面向第一版生产部署：单台 Ubuntu 服务器、PostgreSQL、systemd 托管应用、 Caddy 负责 HTTPS 反向代理。当前预计约 10 人使用，这个方案足够轻、也方便后续迭代。

推荐服务器 Ubuntu 22.04/24.04，Python 3.11+，2 vCPU，4 GB RAM，80 GB SSD 起步。
部署分支 当前代码分支是 codex-architecture-cleanup；合并到 main 后可改为 main。
数据策略 PostgreSQL 存业务数据和原始上传文件，备份以数据库为主。
总览 服务器准备 PostgreSQL 应用部署 AKTA/反向翻译 systemd HTTPS 备份恢复 后续迭代 上线检查

1. 总览

部署可以理解成四件事：把代码放到服务器、准备生产数据库、让应用作为后台服务长期运行、 再用 HTTPS 域名把服务暴露给用户。

步骤 做什么 意义
服务器准备 安装 Git、Python、PostgreSQL、Caddy，创建专用系统用户。 隔离运行环境，避免应用直接用 root 权限运行。
PostgreSQL 创建数据库和数据库账号，配置 PROTEINHUB_DATABASE_URL。 生产数据集中存储，支持多人使用、备份和恢复。
应用服务 拉取 GitHub 代码，创建虚拟环境，安装依赖。 保证服务器运行的就是仓库里可追踪的版本。
反向代理 Caddy 接管 80/443 端口并转发到本机 8080。 自动 HTTPS，用户访问域名即可使用。
备份与发布 每次升级前备份，升级后跑测试和健康检查。 让后续迭代可回退、可验证。

2. 服务器准备

先用 SSH 登录服务器。下面命令默认系统是 Ubuntu。

ssh your-user@your-server-ip

安装基础依赖：

sudo apt update
sudo apt install -y git postgresql postgresql-contrib curl gnupg software-properties-common
python3 --version

ProteinHub 要求 Python 3.11 或更高版本。Ubuntu 22.04 / Pop!_OS 常见默认 python3 是 3.10，需要额外安装 Python 3.11。 

python3.11 --version

如果上面命令提示找不到 python3.11，先尝试：

sudo apt install -y python3.11 python3.11-venv python3.11-dev

如果 apt 源里也找不到，再添加 deadsnakes PPA 后安装：

sudo add-apt-repository -y ppa:deadsnakes/ppa
sudo apt update
sudo apt install -y python3.11 python3.11-venv python3.11-dev
python3.11 --version

Pop!_OS/Ubuntu 默认 apt 源里可能没有 caddy 包。按 Caddy 官方 Debian/Ubuntu 包安装方式添加 apt 源后再安装： 

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy
caddy version

创建 proteinhub 系统用户和目录。应用以后用这个用户运行， 数据目录放在 /var/lib/proteinhub，代码放在 /opt/proteinhub。 

sudo useradd --system --home-dir /var/lib/proteinhub --shell /usr/sbin/nologin proteinhub
sudo mkdir -p /opt/proteinhub /var/lib/proteinhub/storage /var/backups/proteinhub /opt/proteinhub-tools
sudo chown -R proteinhub:proteinhub /var/lib/proteinhub /var/backups/proteinhub /opt/proteinhub
sudo chmod 700 /var/backups/proteinhub
意义：这一步把“系统、代码、数据、备份、外部工具”分开放，后续迁移和排错会清楚很多。

3. PostgreSQL

创建数据库用户和数据库。输入密码时请记录下来，下一步会写入环境变量。

sudo -u postgres createuser proteinhub --pwprompt
sudo -u postgres createdb proteinhub -O proteinhub

检查数据库连接：

psql "postgresql://proteinhub:<password>@127.0.0.1:5432/proteinhub" -c "select 1;"

ProteinHub 启动时会初始化当前 schema。正式上线后，任何涉及数据库结构的代码更新， 都应该先备份，再发布。

注意：生产环境建议不要继续用 SQLite。多人访问、原始文件入库、备份恢复这些事情， PostgreSQL 更稳。

4. 应用部署

从 GitHub 拉取代码。如果仓库是公开的，最省事的是先把目录让当前用户可写， 再用 HTTPS clone；如果仓库是私有的，就给执行 clone 的那个用户配置 GitHub SSH key 或 PAT。 如果当前改动还没合并到 main，就先部署当前分支。 

sudo mkdir -p /opt/proteinhub
sudo chown -R "$USER":"$USER" /opt/proteinhub
git clone https://github.com/Haoyu-Ding/ProteinHub.git /opt/proteinhub
sudo chown -R proteinhub:proteinhub /opt/proteinhub
cd /opt/proteinhub
sudo -u proteinhub git checkout codex-architecture-cleanup
sudo -u proteinhub git pull --ff-only

创建 Python 3.11 虚拟环境并安装依赖。如果之前误用 Python 3.10 创建过 .venv，先删掉旧环境再重建： 

cd /opt/proteinhub
sudo rm -rf .venv
sudo -u proteinhub python3.11 -m venv .venv
sudo -u proteinhub .venv/bin/python -m pip install -U pip setuptools wheel
sudo -u proteinhub .venv/bin/pip install -e ".[dev]"

安装完成后先确认虚拟环境确实是 Python 3.11+，再跑一次项目检查：

cd /opt/proteinhub
sudo -u proteinhub .venv/bin/python --version
sudo -u proteinhub .venv/bin/python -m pytest
sudo -u proteinhub .venv/bin/python -m compileall -q proteinhub tests main.py

后续在 /opt/proteinhub 里拉代码时，也用 proteinhub 用户执行， 避免 Git 因为目录所有者不同报 dubious ownership： 

sudo -u proteinhub git -C /opt/proteinhub pull --ff-only

复制环境变量模板：

sudo cp /opt/proteinhub/.env.example /etc/proteinhub.env
sudo chown root:proteinhub /etc/proteinhub.env
sudo chmod 640 /etc/proteinhub.env
sudo editor /etc/proteinhub.env

至少要改这些配置：

变量 建议值 意义
PROTEINHUB_DATABASE_URL postgresql://proteinhub:<password>@127.0.0.1:5432/proteinhub 让应用连接生产 PostgreSQL。
PROTEINHUB_ARTIFACT_STORAGE_BACKEND database 原始上传文件和 artifact bytes 直接存数据库。
PROTEINHUB_JWT_SECRET 长随机字符串 签发和验证登录 token。
PROTEINHUB_NICEGUI_STORAGE_SECRET 另一个长随机字符串 保护 NiceGUI 本地会话状态。
PROTEINHUB_ADMIN_EMAILS 管理员邮箱，多个用英文逗号分隔 决定谁可以进入管理员功能，例如删除项目。

生成 secret 的命令：

python3.11 -c "import secrets; print(secrets.token_urlsafe(48))"

如果你已经完成依赖安装，从这里继续

你刚执行完 pip install -e ".[dev]" 后，下一步就是创建并编辑生产环境变量文件：

sudo cp /opt/proteinhub/.env.example /etc/proteinhub.env
sudo chown root:proteinhub /etc/proteinhub.env
sudo chmod 640 /etc/proteinhub.env
sudo editor /etc/proteinhub.env

编辑时至少替换成你的真实值：

PROTEINHUB_DATABASE_URL=postgresql://proteinhub:<真实数据库密码>@127.0.0.1:5432/proteinhub
PROTEINHUB_ARTIFACT_STORAGE_BACKEND=database
PROTEINHUB_JWT_SECRET=<python3.11 生成的长随机字符串>
PROTEINHUB_NICEGUI_STORAGE_SECRET=<另一个长随机字符串>
PROTEINHUB_ADMIN_EMAILS=<你的管理员邮箱>
PROTEINHUB_DATA_DIR=/var/lib/proteinhub
PROTEINHUB_STORAGE_DIR=/var/lib/proteinhub/storage

保存后按下面第 5-8 步继续：可选外部工具、安装 systemd service、健康检查、 选择访问方式、设置备份。

5. AKTA 和反向翻译外部工具

这一节是可选步骤。先部署主系统时可以不配置；ProteinHub 仍然可以登录、 建项目、建蛋白、上传 HPLC/SPR 等数据。

现在先跑起来：跳过外部工具

如果你只是先把网站跑起来，就执行这个检查命令，然后继续第 6 步：

cd /opt/proteinhub
sudo -u proteinhub .venv/bin/python scripts/check-external-tools.py \
  --env-file /etc/proteinhub.env

看到 AKTA 或 domesticator 显示未配置也没关系，只要命令没有失败即可。 不要在 /etc/proteinhub.env 里填写不存在的路径。

启用 AKTA/domesticator

如果你现在就要启用 AKTA zip 渲染或批次 DNA 优化，再继续下面的配置。 不建议把本地 .legacy/ 虚拟环境直接提交到主仓库。服务器上单独准备外部工具目录： 

/opt/proteinhub-tools/
  akta/
    bin/python
    akta_hap.py
  domesticator-env/
    bin/python
  domesticator/
    domesticator.py
    database/

然后在 /etc/proteinhub.env 中配置实际路径：

PROTEINHUB_AKTA_HAP_PYTHON=/opt/proteinhub-tools/akta/bin/python
PROTEINHUB_AKTA_HAP_SCRIPT=/opt/proteinhub-tools/akta/akta_hap.py

PROTEINHUB_LEGACY_DOMESTICATOR_PYTHON=/opt/proteinhub-tools/domesticator-env/bin/python
PROTEINHUB_LEGACY_DOMESTICATOR_SCRIPT=/opt/proteinhub-tools/domesticator/domesticator.py
PROTEINHUB_LEGACY_DOMESTICATOR_DATABASE=/opt/proteinhub-tools/domesticator/database

domesticator-env 是 Python/conda 环境；domesticator 是脚本和 database 目录。不要把 conda 环境直接建在已有 domesticator.py 和 database/ 的目录里。

如果服务器上已经有 domesticator.py 和 database/， 但 /opt/proteinhub-tools/domesticator/bin/python 不存在，按下面方式创建单独环境： 

sudo rm -rf /opt/proteinhub-tools/domesticator-env
sudo chown -R zhaojiao:zhaojiao /opt/proteinhub-tools
~/anaconda3/bin/conda create -y --override-channels -c conda-forge -p /opt/proteinhub-tools/domesticator-env python=3.7 pip
/opt/proteinhub-tools/domesticator-env/bin/python -m pip install "pip<24.1" "setuptools==57.5.0" wheel
/opt/proteinhub-tools/domesticator-env/bin/pip install dnachisel==1.1 biopython==1.72 CAI==1.0.3 scipy==1.4.1 tqdm==4.64.1
sudo chown -R proteinhub:proteinhub /opt/proteinhub-tools

如果你用的是 miniforge，把 conda 命令换成：

~/miniforge3/bin/conda create -y --override-channels -c conda-forge -p /opt/proteinhub-tools/domesticator-env python=3.7 pip

--override-channels 用来绕过服务器本机 conda 配置里的失效镜像源。 不要再检查 /opt/proteinhub-tools/domesticator/bin/python； 正确 Python 路径是 /opt/proteinhub-tools/domesticator-env/bin/python。 CAI==1.0.3 是旧包，所以 domesticator 环境需要先固定 setuptools==57.5.0。

然后确认这些文件真的存在：

sudo -u proteinhub test -x /opt/proteinhub-tools/akta/bin/python
sudo -u proteinhub test -f /opt/proteinhub-tools/akta/akta_hap.py
sudo -u proteinhub test -x /opt/proteinhub-tools/domesticator-env/bin/python
sudo -u proteinhub test -f /opt/proteinhub-tools/domesticator/domesticator.py
sudo -u proteinhub test -d /opt/proteinhub-tools/domesticator/database

上线前检查外部工具是否可用：

cd /opt/proteinhub
sudo -u proteinhub .venv/bin/python scripts/check-external-tools.py \
  --env-file /etc/proteinhub.env \
  --require-akta \
  --require-domesticator
意义：主应用保持干净可部署；AKTA 和 xiaopang/domesticator 这类历史脚本作为可替换工具接入。

6. systemd 后台服务

你现在从这里继续

如果第 5 步外部工具检查已经显示 AKTA 和 Legacy domesticator 都是 configured 且每个路径都是 ok，就按下面顺序继续。

先在服务器上跑一次代码检查：

cd /opt/proteinhub
sudo -u proteinhub .venv/bin/python -m pytest
sudo -u proteinhub .venv/bin/python -m compileall -q proteinhub tests main.py

然后安装并启动后台服务：

sudo cp /opt/proteinhub/deploy/proteinhub.service /etc/systemd/system/proteinhub.service
sudo systemctl daemon-reload
sudo systemctl enable --now proteinhub
sudo systemctl status proteinhub

systemctl status 页面如果占住终端，按 q 退出。 服务启动后立刻做本机健康检查： 

curl http://127.0.0.1:8080/api/health

期望看到 "status":"ok"、"database":"ok"、"storage":"ok"。

如果健康检查失败，先看最近日志：

journalctl -u proteinhub -n 100 --no-pager

健康检查通过后，先按内网模式配置 Caddy：

sudo cp /opt/proteinhub/deploy/Caddyfile.lan.example /etc/caddy/Caddyfile
sudo systemctl reload caddy
hostname -I
curl http://127.0.0.1/api/health

记下 hostname -I 输出里的内网 IP，同一网络里的电脑访问 http://<内网 IP>/。

最后先做一次手动备份，确认备份链路可用：

sudo -u proteinhub PROTEINHUB_ENV_FILE=/etc/proteinhub.env /opt/proteinhub/scripts/backup-postgres.sh
做到这里，第一版内网部署就跑起来了。接下来用 scripts/create-user.py 在服务器上创建管理员账号，再进入浏览器登录， 创建一个项目和蛋白，最后试一次 HPLC/SPR/AKTA 上传。

7. 访问方式：公网域名或只用内网

先确认服务本机可用。如果这一步返回 status: ok， 再选择“只在内网使用”或“公网域名访问”。 

curl http://127.0.0.1:8080/api/health

只在内网使用

这种方式不需要域名，也不需要公网 IP。适合先在实验室、办公室、同一局域网 或 VPN/Tailscale 网络里给少数人使用。

查看服务器内网 IP：

hostname -I

假设看到的内网 IP 是 10.6.108.62，复制内网 Caddy 模板：

sudo cp /opt/proteinhub/deploy/Caddyfile.lan.example /etc/caddy/Caddyfile
sudo systemctl reload caddy

如果服务器启用了 UFW 防火墙，放行 80 端口：

sudo ufw allow 80/tcp
sudo ufw status

同一内网的用户访问：

http://10.6.108.62/
意义：内网模式最省事，不依赖域名和公网入站能力，很适合第一版先给小团队试用。

用公网域名访问

在域名服务商的 DNS 控制台添加一条 A 记录：主机记录填 proteinhub， 记录值填服务器公网 IP。生效后用户访问 https://proteinhub.example.com/。

如果服务器在家里、学校或公司内网里，通常没有公网入站能力；这时只配 DNS 不会生效， 还需要路由器端口转发、云服务器、公网反向代理、frp、Tailscale 或 Cloudflare Tunnel 这类方案。

确认 80/443 端口可从公网访问后，复制公网 Caddy 模板：

sudo cp /opt/proteinhub/deploy/Caddyfile.example /etc/caddy/Caddyfile
sudo editor /etc/caddy/Caddyfile
sudo systemctl reload caddy

把 your-domain.example.com 替换成真实域名。Caddy 会自动申请和续期 HTTPS 证书。

如果服务器启用了 UFW 防火墙，放行 80/443：

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status

检查外网访问：

curl https://your-domain.example.com/api/health
意义：公网域名适合正式给外部用户使用；应用本身仍然只监听本机 8080。

8. 备份和恢复

先跑一次手动备份，确认备份脚本可用：

sudo -u proteinhub PROTEINHUB_ENV_FILE=/etc/proteinhub.env /opt/proteinhub/scripts/backup-postgres.sh

安装每天自动备份：

sudo cp /opt/proteinhub/deploy/proteinhub-backup.service /etc/systemd/system/proteinhub-backup.service
sudo cp /opt/proteinhub/deploy/proteinhub-backup.timer /etc/systemd/system/proteinhub-backup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now proteinhub-backup.timer
sudo systemctl list-timers proteinhub-backup.timer

这个 timer 会每天凌晨 02:15 备份一次。如果服务器当时关机， 开机后会补跑一次。默认只做本机备份；如果 /etc/proteinhub.env 里配置了远程备份目标， 本机备份成功后会把这一次新生成的 dump 同步过去。立即测试一次自动备份： 

sudo systemctl start proteinhub-backup.service
sudo journalctl -u proteinhub-backup.service -n 50 --no-pager
ls -lh /var/backups/proteinhub

默认本地备份保留 14 天；可以在 /etc/proteinhub.env 里用 PROTEINHUB_BACKUP_RETENTION_DAYS=30 之类的值调整。

远程备份同步配置示例：

PROTEINHUB_REMOTE_BACKUP_TARGET=dinghy@10.6.108.61:/mnt/data/proteinhub-backups/dumps/
PROTEINHUB_REMOTE_BACKUP_SSH_KEY=/var/lib/proteinhub/.ssh/proteinhub_backup

配置远程同步前，先确认 proteinhub 用户能免密连接备份服务器：

sudo -u proteinhub ssh -i /var/lib/proteinhub/.ssh/proteinhub_backup \
  -o IdentitiesOnly=yes \
  dinghy@10.6.108.61 'echo ok'

恢复流程要先停服务，恢复后再启动：

sudo systemctl stop proteinhub
sudo -u proteinhub PROTEINHUB_ENV_FILE=/etc/proteinhub.env /opt/proteinhub/scripts/restore-postgres.sh /var/backups/proteinhub/proteinhub_YYYYmmdd_HHMMSS.dump
sudo systemctl start proteinhub
注意：现在原始文件也会进数据库，所以数据库备份就是生产数据的核心备份。建议定期把备份同步到服务器外部位置。

9. 后续迭代流程

每次发布建议按固定顺序来，少靠记忆：

  1. 本地开发并运行测试。
  2. 提交到 GitHub。
  3. 服务器先备份 PostgreSQL。
  4. 服务器拉取新代码并安装依赖。
  5. 服务器跑测试和编译检查。
  6. 重启 systemd 服务。
  7. 访问 /api/health 和几个关键页面。
cd /opt/proteinhub
sudo -u proteinhub PROTEINHUB_ENV_FILE=/etc/proteinhub.env scripts/backup-postgres.sh
sudo -u proteinhub git fetch origin
sudo -u proteinhub git checkout codex-architecture-cleanup
sudo -u proteinhub git pull --ff-only
sudo -u proteinhub .venv/bin/pip install -e ".[dev]"
sudo -u proteinhub .venv/bin/python -m pytest
sudo -u proteinhub .venv/bin/python -m compileall -q proteinhub tests main.py
sudo systemctl restart proteinhub
curl http://127.0.0.1:8080/api/health

回退策略

如果发布后发现问题，优先回退代码；如果数据库也被错误迁移或污染，再恢复数据库备份。

cd /opt/proteinhub
sudo -u proteinhub git log --oneline -5
sudo -u proteinhub git checkout <previous-good-commit>
sudo systemctl restart proteinhub
curl http://127.0.0.1:8080/api/health

10. 上线前检查清单

  • GitHub 上能看到当前提交。
  • /etc/proteinhub.env 已替换所有 secret 和数据库密码。
  • PROTEINHUB_ARTIFACT_STORAGE_BACKEND=database。
  • /api/health 返回 status: ok。
  • 管理员账号可以登录，管理员邮箱在 PROTEINHUB_ADMIN_EMAILS 中。
  • 可以创建项目、创建蛋白、上传 HPLC/SPR/AKTA 数据。
  • HPLC 图里小于 0.01 min 的分段不会绘制。
  • 蛋白详情页实验结果没有删除按钮。
  • 备份脚本能生成 dump 文件，且备份目录权限正确。
  • Caddy HTTPS 可访问，浏览器没有证书警告。
做完这份清单后，ProteinHub 第一版生产部署就可以给小团队使用了。后续迭代继续走“本地测试、提交 GitHub、服务器备份、拉代码、重启验证”的节奏。
